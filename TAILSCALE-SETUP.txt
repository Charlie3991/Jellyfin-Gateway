================================================================================
 JELLYFIN GATEWAY - TAILSCALE ACCESS ON LINUX
 Installation, firewall options, NordVPN coexistence, and troubleshooting
================================================================================

 This guide uses the gateway's default TCP port, 8390, and Tailscale's IPv4
 address. Replace <gateway-tailnet-ip>, <gateway-hostname>, and
 <project-directory> with your own values. Use your configured port if it
 differs. Run commands on the gateway host unless a step says "client".

 The basic setup works with or without NordVPN. Systemd commands apply to
 distributions using systemd; other systems need their own service manager.
 Examples assume a regular Linux host with the tailscale0 interface, rather
 than a container or Tailscale userspace networking.

--------------------------------------------------------------------------------
 1. INSTALL TAILSCALE FOR YOUR DISTRIBUTION
--------------------------------------------------------------------------------

 Debian, Ubuntu, Linux Mint, Raspberry Pi OS, Fedora/RHEL derivatives,
 openSUSE/SUSE, and other distributions supported by Tailscale's installer:

   curl -fsSL https://tailscale.com/install.sh -o /tmp/tailscale-install.sh
   less /tmp/tailscale-install.sh
   sh /tmp/tailscale-install.sh

 The official script selects the distribution's package manager and asks
 for sudo when needed. Install curl first if it is missing, using your
 distribution's package manager. For manual repository/key setup, choose
 your exact distribution and version at:
   https://pkgs.tailscale.com/stable/

 After adding the appropriate package repository, the package commands are:
   Debian/Ubuntu:  sudo apt-get update && sudo apt-get install tailscale
   Fedora/RHEL:    sudo dnf install tailscale
   openSUSE/SUSE:  sudo zypper refresh && sudo zypper install tailscale

 Arch Linux and derivatives with Tailscale in their repositories:
   sudo pacman -S tailscale

 NixOS: enable the service in your NixOS configuration, then rebuild:
   services.tailscale.enable = true;

 For other distributions, use Tailscale's Linux installation instructions,
 including the static binaries if no supported package is available:
   https://tailscale.com/docs/install/linux

 On systemd hosts, start the daemon and connect:
   sudo systemctl enable --now tailscaled
   sudo tailscale up
   tailscale status
   tailscale ip -4

 Follow the sign-in URL and approve the device in the tailnet admin console
 if your policy requires it. Save the IPv4 address printed by the last
 command; this is <gateway-tailnet-ip>.

 On non-systemd hosts, enable tailscaled using your distribution's service
 manager, then run sudo tailscale up. The project's systemd user units are
 optional; the gateway can also be started manually as described in README.

--------------------------------------------------------------------------------
 2. CONFIGURE AND CHECK THE GATEWAY
--------------------------------------------------------------------------------

 In <project-directory>/.env, set:
   GATEWAY_HOST=0.0.0.0
   GATEWAY_PORT=8390

 Keep your existing qBittorrent and Jellyfin settings. Restart the gateway
 using the method you installed it with. For the project's systemd user unit:
   systemctl --user restart jellyfin-gateway
   systemctl --user status jellyfin-gateway

 For a manual installation, restart ./run.sh from the project directory.
 Adjust the systemd unit's project/venv paths if using the supplied units.

 Check locally:
   curl --max-time 10 -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8390/
   ss -ltn 'sport = :8390'

 Expect HTTP 200 and a listener on 0.0.0.0:8390. Binding to 127.0.0.1 alone
 prevents direct access over tailscale0. Binding to 0.0.0.0 also permits LAN
 access when the firewall allows it. For an IPv4 tailnet-only listener, use
 the host's Tailscale IPv4 address as GATEWAY_HOST instead, ensuring
 tailscaled is ready before the gateway starts.

 This setup needs neither a subnet router nor an exit node. Do not select a
 Tailscale exit node on the gateway as part of these steps.

--------------------------------------------------------------------------------
 3. ALLOW ACCESS THROUGH YOUR EXISTING FIREWALL
--------------------------------------------------------------------------------

 Use the firewall manager already configured on your host. Do not install
 and enable UFW alongside firewalld just to follow this guide. Preserve
 existing SSH/management access when changing firewall configuration.

 UFW (common on Ubuntu/Debian; also available on other distributions):
   sudo ufw status verbose
   sudo ufw allow in on tailscale0 to any port 8390 proto tcp

 If UFW is inactive, the rule is saved but UFW does not enforce it. Enabling
 a firewall for the first time requires reviewing the host's other services.

 firewalld (common on Fedora/RHEL/openSUSE):
   sudo firewall-cmd --state
   sudo firewall-cmd --get-active-zones

 For a dedicated gateway zone, create it once, then configure and apply it:
   sudo firewall-cmd --permanent --new-zone=jellyfin-tailnet
   sudo firewall-cmd --permanent --zone=jellyfin-tailnet --add-port=8390/tcp
   sudo firewall-cmd --permanent --zone=jellyfin-tailnet --change-interface=tailscale0
   sudo firewall-cmd --reload
   sudo firewall-cmd --zone=jellyfin-tailnet --list-all

 If that zone already exists, skip --new-zone. Moving tailscale0 into this
 zone can change access to other tailnet services, including SSH. If you
 need those services, retain their explicit rules or modify the interface's
 existing zone instead. Recheck the active zone after a restart.

 Direct nftables/iptables or another firewall manager:
 Add a persistent input rule for TCP/8390 arriving on tailscale0 using your
 existing ruleset's conventions. Table names, chain names, and persistence
 files vary. An appended allow rule after a matching drop cannot help.

 IMPORTANT: Tailscale also manages firewall rules by default. Depending on
 the backend and rule ordering, its own rules may accept tailnet traffic
 before a UFW per-port rule is reached. The commands above do not prove that
 every other tailnet port is blocked. Use tailnet access policy (grants or
 ACLs) to restrict who can reach the host and which ports they can use.
 Leave normal Tailscale netfilter management enabled unless you are managing
 its complete firewall integration yourself. Do not delete ts-input:
 it can be a Tailscale-managed chain, not a leftover from a manual setup.

 No router port forwarding or public TCP/8390 rule is needed for tailnet
 access. Tailscale transport connectivity is separate from the gateway's
 application port; see the official firewall guidance in section 9.

--------------------------------------------------------------------------------
 4. CONNECT FROM ANOTHER DEVICE
--------------------------------------------------------------------------------

 Install Tailscale on the client (Linux, Windows, macOS, Android, or iOS),
 sign in to the same tailnet or use an approved device-sharing arrangement,
 and ensure the tailnet policy permits TCP/8390 to this host.

 Open:
   http://<gateway-tailnet-ip>:8390

 With working MagicDNS, you can also use:
   http://<gateway-hostname>:8390

 Use the IPv4 address first when troubleshooting. A hostname can resolve
 to IPv6 too, which requires an IPv6 listener and compatible firewall/VPN
 configuration; the 0.0.0.0 example above is IPv4.

 Sign in using a Jellyfin account. Gateway administrators are users with
 Jellyfin administrator permission. Tailscale reachability does not replace
 the application's login or administrator checks.

 Verify from a client, not just from the gateway host:
   tailscale ping <gateway-tailnet-ip>
   curl --max-time 15 -v http://<gateway-tailnet-ip>:8390/

 An HTTP response confirms the application connection. tailscale ping by
 itself does not prove that the TCP port is reachable. A DERP-relayed
 connection is valid; direct connectivity is not required for the dashboard.

--------------------------------------------------------------------------------
 5. IF NORDVPN RUNS ON THE SAME LINUX HOST
--------------------------------------------------------------------------------

 Skip this section if NordVPN is not installed. Use NordVPN's installation
 instructions and supported-distribution list for the Linux client; Tailscale
 support on a distribution does not imply NordVPN support there.

 First establish that client access works without NordVPN connected. If
 you temporarily disconnect it for diagnosis, pause active torrents first
 and confirm the gateway/standalone VPN guard is enabled.

 Inspect the installed client's supported syntax:
   nordvpn --version
   nordvpn status
   nordvpn settings
   nordvpn help

 For versions supporting the allowlist command:
   nordvpn allowlist --help
   nordvpn allowlist add subnet 100.64.0.0/10

 Some versions/documentation use "whitelist" instead:
   nordvpn whitelist --help
   nordvpn whitelist add subnet 100.64.0.0/10

 Use the spelling supported by your installed client, then check
 nordvpn settings and retest TCP/8390 with NordVPN connected. This exception
 covers Tailscale's IPv4 peer range; it does not grant tailnet access-policy
 permissions. Keep the VPN firewall and kill switch enabled.

 If using IPv6, subnet routes, or another VPN client, its supported
 exceptions must cover the relevant addresses too. Do not assume an IPv4
 exception covers those cases. See the VPN coexistence reference below.

 Recheck after reconnecting NordVPN and after rebooting. A subnet exception
 may be enough, but routing, DNS, or other firewall rules can still conflict.

--------------------------------------------------------------------------------
 6. ADVANCED: HOST-SPECIFIC VPN BYPASS DIAGNOSIS
--------------------------------------------------------------------------------

 Use this section only if the basic setup works and the VPN breaks it.

 Collect the actual configuration while both daemons are running:
   ip -4 rule show
   ip -4 route show table all
   ip -4 route get <client-tailnet-ip>
   nordvpn settings
   sudo nft -a list ruleset

 If nft is unavailable, install your distribution's nftables diagnostic
 tool, or use the host's iptables tools:
   sudo iptables-save
   sudo ip6tables-save

 Separate two cases:
 - Replies to tailnet peers need the Tailscale route and a firewall exception.
 - tailscaled's control/relay traffic uses internet destinations. If the VPN
   blocks that traffic, an exception for 100.64.0.0/10 alone cannot cover it.

 Prefer the VPN client's supported coexistence/exclusion settings. Custom
 packet-mark/cgroup rules require matching the installed client's routing
 and firewall behavior. A mark alone does not override a later drop.

 An earlier machine-specific recipe used mark 0xe1f1, routing table 205,
 and cgroup system.slice/tailscaled.service. Those are examples from that
 host, not portable settings. Do not paste them into a different system
 without verifying the mark/mask, rule order, VPN technology, and cgroup.

 On systemd hosts, discover the daemon's actual cgroup:
   systemctl show tailscaled.service -p ControlGroup

 A cgroup-based nft rule additionally needs cgroup v2 and kernel/nft support
 for that match. It must be installed after the daemon's cgroup exists.
 Recheck it after tailscaled restarts, VPN reconnects, and firewall reloads;
 a boot-only oneshot does not guarantee it stays correct.

 nftables processes base chains by hook priority. An accept ends evaluation
 of its chain, but a later base chain can still drop the packet. Inspect all
 relevant input/output chains; never assume "the first accept wins".

 If you already have a custom tailscale-vpn-bypass service, review it using:
   systemctl cat tailscale-vpn-bypass.service
   journalctl -u tailscale-vpn-bypass.service -b --no-pager

 There is no universal bypass unit to install from this guide. Keep any
 verified host-specific workaround separate from the portable setup.

--------------------------------------------------------------------------------
 7. TROUBLESHOOTING AND REBOOT CHECKS
--------------------------------------------------------------------------------

 Local HTTP request fails:
   Check the gateway process, .env, listener, and Jellyfin configuration.
   systemctl --user status jellyfin-gateway
   journalctl --user -u jellyfin-gateway -b --no-pager

 Local HTTP works, but client TCP/8390 times out:
   Check tailscale status on both devices, device approval/key expiry,
   tailnet grants/ACLs, incoming-connection blocking ("shields up"), host
   firewall rules, and the gateway bind address. If it only fails with the
   VPN connected, inspect the subnet exception and routes (sections 5-6).

 IP address works, but hostname fails:
   Check MagicDNS, the client's resolver, and VPN DNS settings. Continue
   using the IPv4 URL while resolving the DNS conflict.

 Node becomes unreachable when the VPN connects:
   tailscale status
   tailscale netcheck
   journalctl -u tailscaled -b --no-pager
   nordvpn status
   Use section 6 to distinguish routing from firewall/transport failures.

 Works until reboot or firewall reload:
   Verify daemon startup, persistent firewall rules, and NordVPN settings.
   On systemd hosts:
     systemctl is-enabled tailscaled
     systemctl status tailscaled
     systemctl --user is-enabled jellyfin-gateway

   A user service normally depends on the user's session. If it must start
   at boot without a login, enable lingering for that user:
     sudo loginctl enable-linger <gateway-user>

   On other init systems, configure the equivalent daemon and gateway
   startup. Shell-added nft/iptables rules are not automatically persistent;
   use your firewall manager's configuration mechanism.

 Final check:
   Test HTTP from another tailnet device with NordVPN connected, after a
   reconnect, and after a reboot. Verify the VPN guard still pauses torrents
   when its configured tunnel disappears before resuming normal downloads.

--------------------------------------------------------------------------------
 8. ACCESS BOUNDARIES
--------------------------------------------------------------------------------

 - Allow only intended users/devices to reach TCP/8390 in the tailnet policy.
   Review overlapping broad grants/ACLs when narrowing access.
 - Keep qBittorrent's WebUI local unless you intentionally expose it. Access
   to the dashboard does not require opening qBittorrent or Jellyfin ports
   to every tailnet member.
 - Store real passwords/API keys in your local .env, not in this guide.
 - Review LAN/public-interface access separately if using GATEWAY_HOST=0.0.0.0.
   This guide adds tailnet access; it does not audit existing firewall rules.
